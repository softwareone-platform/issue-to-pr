## What this repo is

A **Claude Code plugin marketplace** for an engineering team. There is no compiled code and no build system — the "source" is almost entirely Markdown (`SKILL.md`, agent `.md`, `README.md`, docs), JSON manifests, and three Python scripts (the dashboard's server and parser, plus a self-check test). The deliverable is skills and subagents that other repos install and invoke.

Distribution is the GitHub marketplace repo `https://github.com/softwareone-platform/issue-to-pr.git` (git origin). Consumers install with `/plugin marketplace add <url>` then `/plugin install <plugin>@itpr`, and activate with `/reload-plugins`.

## Repository layout

```
.claude-plugin/marketplace.json      # THE registry — lists every published plugin, its version + source path
plugins/<plugin>/
├── .claude-plugin/plugin.json        # plugin metadata: name, description, version, optional dependencies[]
├── skills/<skill>/SKILL.md           # a user-invocable skill (frontmatter + body)
├── skills/<skill>/evals/evals.json   # skill evals (prompt → expected behaviour + assertions)
├── skills/<skill>/README.md          # optional per-skill doc
├── agents/<agent>.md                 # a subagent (flat dir, bare-name files) — test-authoring only
├── resources/                        # templates / static assets bundled with the plugin
└── docs/                             # deeper design docs
```

`.claude/` is **gitignored** (see `.gitignore`) — it holds local session state, and in *consumer* repos it is where `setup-test-context` writes the generated conventions. Never rely on it being present in this repo.

## Anatomy of a skill

A skill is `skills/<name>/SKILL.md` with YAML frontmatter (`name`, `description`) followed by a Markdown body of instructions. Invoked as `/<plugin>:<skill>` or auto-triggered.

The `description` field is **load-bearing**: it is how Claude decides when to auto-trigger the skill. It typically packs three things — what the skill does, "Use when…" trigger phrases, and an explicit "Do NOT trigger for…" list that routes look-alike requests to sibling skills. Preserve this structure and do not compress or shorten descriptions casually; terse descriptions break triggering.

**Description length cap**: there are two caps and the binding one is **not** Claude Code's. The Agent Skills specification — the open format these files are written in, which 26+ agents now read — caps `description` at **1,024 characters**, and the reference validator (`skills-ref validate`) fails anything longer. Claude Code separately truncates at **1,536** (`skillListingMaxDescChars` default) *(external — a Claude Code internal, not checkable from this repo)*, silently hiding whatever sits past it, and the trailing "Do NOT trigger for…" list is exactly what gets cut. So measure the whitespace-normalized length against **1,024** and keep a new description **≤ ~1,000** for headroom — measure it with `PYTHONUTF8=1 uvx --from "git+https://github.com/agentskills/agentskills@main#subdirectory=skills-ref" skills-ref read-properties <skill-dir>` (there is no installed `skills-ref` on PATH — the bare command does not run), never a hand-rolled fold and never the validator without that prefix (see "Measuring anything" for why both mislead, in opposite directions). If space is tight, cut how-it-works mechanism detail (the body covers that after invoke) and quotes that duplicate the trigger-phrase list — never the "Do NOT trigger for…" routing. **This entry used to say ≤ ~1,450, a target derived from the Claude Code cap alone, and 7 of the 14 shipped descriptions were over the spec limit because of it** (#14) — the same ship-behaviour-not-observation failure as the commit-format rules in #12. All 14 skill and 8 agent descriptions were measured and brought under 1,024 on 2026-08-31; the longest is now `resolve-pr-comments` at 997 and the shortest `add-unit-test-agent` at 286. Two limits on this: the old entry's own figure did not reproduce — it named `review-issue-fact` at 1,436 as the longest, but measured on 2026-08-31 that description was 1,290 and the longest was `review-plan-risk` at 1,355 — and whether a given harness rejects, truncates, or ignores an over-length description is *(external)*, unverified for every harness including Claude Code; only the validator's behaviour is confirmed.

## Subagents (test-authoring)

Only `test-authoring` ships subagents, in a flat `agents/` dir with bare-name files (e.g. `add-unit-test-agent.md`). Frontmatter carries `name` (bare) and `description` — **and deliberately no `model:`**. At runtime Claude Code applies the plugin namespace, so they are spawned as `Agent(subagent_type="test-authoring:<agent-name>")`.

**Do not add `model:` to an agent's frontmatter.** It overrides the model the user chose for their session, and this is a publicly-installed plugin: picking the cost/quality trade-off is the consumer's call, not ours. The predecessor plugin (`swo/mpt-test-skills`) pinned `model: sonnet` on all 12 of its agents — that was an internal plugin, and it is not the precedent to follow here. Its absence is a decision, not an oversight; if cost guidance is wanted, put a measured figure in the README and let the consumer choose.

The architecture is **orchestrator → writer → verifier**:
- A skill body is the *orchestrator* (top-level caller). It resolves scope, delegates to writer agents, spawns read-only verifier agents, and runs the fix→verify loop.
- Writers generate/update tests. Verifiers are strictly read-only and report violations.
- **Subagents CAN spawn subagents, up to a depth limit.** This corrects a claim that stood here for months, marked unverifiable — "a subagent cannot spawn another subagent" — and was described as the thing the whole orchestrator/writer/verifier split rests on. It does not rest on it, because the prohibition does not exist. Verified 2026-08-28 two ways: Claude Code's own docs (`code.claude.com/docs/en/sub-agents.md`) state that nesting works recursively to a **default depth of 3 layers total** (main -> L1 -> L2 -> L3), that at the limit the `Agent` tool is simply **withheld**, and that the limit is set by `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (`"1"` disables nesting entirely); and directly, by running `review-plan-risk` inside a subagent, which spawned its own finder fan-out one level below and returned their merged results. A separate cap, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, defaults to 20 concurrent subagents. Neither variable is set on this machine.
- **So the writer/verifier split is a design choice, not a substrate limit — but keep it.** Writers and verifiers still emit structured output for the orchestrator to merge rather than spawning follow-ups themselves, because a verifier that can spawn its own helpers stops being the independent read the orchestrator needed. What changes is which arguments are available: "the runtime forbids it" is not one of them, and an argument that leans on it is unsupported.
- **What the depth limit does constrain is where a skill is invoked from.** A skill whose body spawns agents costs one layer at whatever depth its caller sits: invoked from the main session its own agents land at depth 1, and from inside a subagent they land at depth 2. That leaves room, but it is a budget, and the failure at the limit is silent — the `Agent` tool is withheld, so a fan-out designed for several blind readers quietly becomes one. Before making any skill spawn a wrapper subagent of its own by default, count the layers its deepest caller would need, and remember that a subagent has **no channel to prompt the human**: `review-plan-risk` run that way returned its findings but could not put its scope gate or its edge-case opt-in to anyone, so a whole tier of its output stayed unactioned.

## test-authoring: what ships vs what is generated

`setup-test-context` is an **optional accelerator**, not a prerequisite. Every test workflow works with or without it:
- **Rule books are never copied.** Every skill and agent reads `resources/templates/{rules,shared}/` from the plugin, in both cases below. A skill resolves that root once in Step -1 and passes it to every subagent (a subagent cannot resolve it itself); if it cannot be resolved, the skill stops rather than running unruled.
- **Without setup**: conventions are discovered from the nearest sibling tests at runtime.
- **With setup** (run once in the consumer repo): the cross-layer map is cached under `.claude/conventions/tests/`, and it is **one or two files, not always two** — `project-architecture.md` always, `common-verification-patterns.md` only when §1.4 found at least one qualifying pattern (layer-common or cross-layer-common). Its absence is the normal outcome on a repo with no such pattern, not a failed run. Nothing else is written per-repo — no rule books, no README, no manifest, and no backup: an overwrite has no undo, and the confirmation gate is the protection.

Distinction that matters when editing content: **rules are non-negotiable**; **conventions are descriptive patterns** that observed sibling tests can override. `resources/templates/rules/` = strict, and shipped; the per-repo `.claude/conventions/tests/` files setup generates = descriptive, and generated. There is no conventions *template* dir, and after the rule books stopped being copied there is no template *filling* either — the shipped files carry no placeholders and every convention file is written from analysis.

`common-*` files are role-lifecycle documents (one per actor: orchestrator/writer/update-writer/verifier); the other rule files are rule books. Put an actor's procedure in its `common-*` file and a constraint in the matching rule book — never both, or the rule drifts into two sources of truth.

**No versioning of the generated files, and no state between runs.** There is no manifest, no recorded hashes, and no per-file `schema_version`: `setup-test-context` knows only the fixed set of paths the current version writes. An existing file at one of those paths is rewritten with no undo — the confirmation gate labels it `OVERWRITE` beforehand, and that is the only protection; anything else under `.claude/{conventions,rules,shared}/tests/` is reported and left alone. Re-running is the refresh, so a template change reaches a repo when someone re-runs setup — nothing detects staleness for them.

## Making changes

- **Editing a skill/agent**: edit the `.md`, then in a consumer session run `/reload-plugins` to pick it up. There is nothing to build.
- **Releasing a version bump**: update the version in **both** the plugin's `.claude-plugin/plugin.json` **and** the corresponding entry in `.claude-plugin/marketplace.json` — they must stay in sync. `marketplace.json` is the registry consumers read.
- **Before pushing, derive which plugins need a bump from the diff — do not recall it.** The cache is keyed by version, so a changed plugin at an unchanged version reaches nobody, and the push looks successful. A late commit touching a *different* plugin than the earlier ones is how this slips (it has, once). Run:
  ```bash
  for n in disconfirm-first pr-lifecycle test-authoring issue-to-pr-pipeline; do
    printf '%-22s changed=%s version=%s
' "$n"       "$(git diff --name-only origin/main HEAD -- plugins/$n | wc -l)"       "$(grep -o '"version": "[^"]*"' plugins/$n/.claude-plugin/plugin.json)"
  done
  ```
  Any plugin with `changed>0` whose version equals the one already on `origin/main` is the bug. **Run it AFTER committing, not against the working tree** — `git diff` cannot see an untracked file, so a plugin whose only change is a *new* file (an added `evals.json`, a new skill dir) reports `changed=0` and the gate silently passes the exact case it exists to catch. Verified 2026-08-13: pre-commit the gate read `test-authoring changed=1`, post-commit `changed=2`. If you must check before committing, `git add` first or read `git status --porcelain` alongside it.
- **Adding a skill**: create `plugins/<plugin>/skills/<skill>/SKILL.md` with `name` + `description` frontmatter; add `evals/evals.json` if it warrants evals.
- **Adding a plugin hook**: no plugin ships one today. If you add one it belongs at `plugins/<plugin>/hooks/hooks.json` *(external, and never exercised — no plugin ships a hook, so this path is unconfirmed)* — a **plugin-root** directory, not inside `.claude-plugin/` and not under `resources/` — and `/reload-plugins` picks it up. Getting the location wrong fails silently: the hook simply never loads.
- **Changing the step registry**: `plugins/issue-to-pr-pipeline/resources/resolve-issue-steps.json` is canonical, and the dashboard's index arithmetic runs over `parse_session.py`'s `STEPS` — which `_load_steps()` builds **from that JSON** whenever it is readable and non-empty (`:42-68`). `_DEFAULT_STEPS` is a fallback reached only on `OSError` / `ValueError` / an empty `steps` list, so on the normal path it is dead code. Keep it in the same order anyway — but know that order-parity is load-bearing only on the fallback path, and two other things bite first:
  - **The fallback is silent.** `JSONDecodeError` subclasses `ValueError`, the `except` body is a bare `pass`, and nothing in the model or `/health` reports that the fallback is in use. So a *malformed* registry edit (a trailing comma, `"steps": []`) resurrects the step you just deleted, with no signal anywhere.
  - **`STEPS` is evaluated once at import** (`:68`), and the dashboard is deliberately long-lived — `SKILL.md` says launch it once and reuse it, and `IDLE_SHUTDOWN_S` is 30 minutes after the last viewer disconnects. A registry edit therefore takes effect on **restart**, not on a browser reload, and a server left running for hours serves an import-time snapshot.

  Removing a step id also needs a redirect in `resolve-issue/SKILL.md`'s State reconcile, so a run whose `state.md` still names it resumes cleanly. (This entry previously claimed the index arithmetic ran over `_DEFAULT_STEPS`. It does not, and that wrong summary was later used to design a test fixture — a reminder that a paraphrase in this file gets trusted as ground truth, so correct it here rather than only in your head.)
- **Ship the behaviour, not the observation.** These plugins are installed by people whose conventions we cannot see, so where a value can be *derived from the consumer's own repo*, ship the derivation — not the value we happened to observe here. This has already gone wrong four times in one place: `ad-hoc <summary>`, `acme-xxxxx <summary>` with a ≤50 cap, a flat prohibition on the `Co-Authored-By` trailer justified as "forbidden team-wide", and a `master`-before-`main` base default. Every one was a correct observation of *this* user's internal repos, published as a rule for everyone. The tell is a literal token nobody would invent independently (`ad-hoc`), or a justification that names an authority the consumer is not under ("team-wide"). The fixes are all the same shape — read the repo (`git log --format=%s` for subject shape and length, `git log --format=%b` for the trailer, `git symbolic-ref refs/remotes/origin/HEAD` for the default branch), match what you find, and keep the old value only as the named fallback for when there is no history to learn from. Note this is a *scope* bug, not a missing feature: `open-pr` already had a real learning pass (`SKILL.md:61`), but `:63` limited it to "presentation only", which is exactly the tier these values were not in. The same reasoning as the `model:` decision above, and stronger — a commit format is enforced by the consumer's hooks and CI, so getting it wrong fails their build rather than just costing them tokens.
- **Adding a guard to a skill or agent** (a check that detects a bad state): four traps, all hit within one change here, and they compound. **(a)** Do not build a detector for a state nobody has observed — that is the argument that killed the invariant-harness proposal, and it applies to guards too. **(b)** Every guard needs a boundary, and each boundary puts some legitimate run on the wrong side; each false positive earns a carve-out, each carve-out is a new mechanism, and the new mechanism is the next review round's weakest link. Prefer cutting the guard to adding a third carve-out. **(c)** A guard's inputs must be something someone is *obliged* to produce — check the producing side's own contract, not just that the value exists somewhere. **(d)** Never put a guard downstream of the party it distrusts: a check asking "did you do what you claimed" must not take its trigger, its file list, or its baseline from the claimant. The worst defect found in both halves of one change was exactly this — a spawn gate keyed on the untrustworthy party's own report. **(e) Inventory before you add — including your own recent work.** Grep for the thing you are about to guard against and read what already covers it. This is not the same as (a): the state may be worth guarding and already guarded. A plan step here was written to make `review-plan-risk` re-check a claim class that `review-issue-fact`'s verifier already challenges bidirectionally — **and those two lines had been added the same morning, by the same session that then wrote the step.** Judgement was not the failure; knowing what was already in hand was.

  The four traps above plus this one share a root worth stating on its own: **every one of those fixes was validated against the artifact, never against the world.** Prose can be perfectly self-consistent while its premise is false, its substrate contract forbids it, or the problem is already solved elsewhere — and a review reads the artifact, so a review is structurally blind to all three. Two cheap correctives, and they are not interchangeable: a **fixture** tests the world (does the premise hold, does the mechanism fire), an **inventory** tests what already exists. Run both before writing the guard, not after.
- **Citing a file from a rule book, or adding any name that crosses a role boundary.** The rule used to be
  "check the citation against the orchestrators' Step -1 reading lists". It has now bitten **four** times
  under that wording, which is three more than a rule needs before you conclude the rule is not the problem.
  Checking meant opening five skill files and reading a section of each, so the check was skipped every time.
  The table below is that check, collapsed to one glance. It was extracted from the files on 2026-08-26 —
  from each skill's Step -1 **Now** / **Never** lists and each agent's own rule-book references — not recalled.

  | Party | Reads | Never opens |
  |---|---|---|
  | **Orchestrator** (all five skills) | `common-orchestrator-flow.md` (immediately), then `test-rules.md`, `fix-protocol.md`, `shared/scope-resolution.md`, `static/status-legend.md` lazily, and `sut-analysis.md` on one narrow path | `common-writer-instructions.md`, `common-verifier-checks.md`, `test-writer-rules.md`, plus `common-update-instructions.md` for the add flows |
  | **Writer** (add and update) | `common-writer-instructions.md`, `test-writer-rules.md`, `test-rules.md`, `sut-analysis.md`, plus `common-update-instructions.md` for update writers | not declared, but it is handed no orchestrator or verifier rule book |
  | **Verifier** (all four) | `common-verifier-checks.md`, its own per-type agent file, `fix-protocol.md`, `test-rules.md` | not declared, but it is handed no writer rule book |

  **The one fact that explains all four bites: `test-rules.md` is the only file all three roles read.**
  Orchestrator and writer otherwise share only `sut-analysis.md`, which the orchestrator opens on a single
  narrow path and is therefore not a general declaration site. So a field, flag, or state that a writer
  produces and an orchestrator must act on has **no shared home by default**, and declaring it once always
  leaves one of them unable to see it.

  Three rules follow, and the third is the one that keeps being missed:

  1. A document on a reader's **Never** list cannot be cited to that reader as the definition of anything it
     must produce or act on. Inline what it needs and say which copy is authoritative.
  2. A name that crosses a role boundary is declared **at both ends**, or in `test-rules.md` if every role
     needs it. Inlining twice is the cheap error here; declaring once is the expensive one.
  3. **A flag is not reachable just because its definition is.** Check the party that must *set* it has a
     field for it in the prompt template it fills, and the party that must *branch* on it is told to look
     for it at the step where the branch happens. Three of the four bites were this: the definition was fine
     and the value had nowhere to travel — a spawn template with no slot for the flag, a handler sitting under
     a heading gated on a signal the producer was told not to send, and a carve-out reachable from one of the
     three callers that needed it.

  The four bites, so the shape is recognisable: `bootstrap_authorisation` and `bootstrap_seed` (each cited
  to a reader forbidden to open the definition), `seed_request` (no slot in the template that had to carry
  it, so the whole feature would have silently never fired), and a U1 carve-out reachable from one add-flow
  caller of three. All four passed a behavioural fixture before a review caught them.
- **Validating**: there is no linter. At minimum verify JSON parses (`marketplace.json`, `plugin.json`, `evals.json`) and that frontmatter is well-formed before committing.

## Running skill evals

Each `evals/evals.json` pairs prompts with an `expected_output` and a list of `assertions`. Author these via the `skill-creator` skill, not a standalone test runner. Coverage is **7 of 14 skills** (`disconfirm-first` 1/3, `pr-lifecycle` 0/2, `test-authoring` 6/6, `issue-to-pr-pipeline` 0/3).

**Three different tools touch evals; do not collapse them into one word ("the runner"). Verified 2026-08-14 by reading the installed `skill-creator` at `~/.claude/plugins/cache/claude-plugins-official/skill-creator/<hash>/skills/skill-creator/`:**

1. **`evals.json` is skill-creator's OWN documented schema, and it has a working consumer.** `references/schemas.md:7` defines it at exactly our path (`evals/evals.json`, with `evals[].prompt` and `evals[].expected_output`), and `SKILL.md:221-234` is the workflow that eats it: run the skill per prompt, spawn a grader subagent (`agents/grader.md`) to judge each assertion into `grading.json`, then `python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>` for `benchmark.json` (pass_rate, time, tokens, mean ± stddev, **and the delta**), then an analyst pass via `agents/analyzer.md` that specifically hunts **"assertions that always pass regardless of skill (non-discriminating)"** — i.e. the discriminating-power check this file elsewhere says we lack. **So our format was never orphaned, and there is nothing to convert.**
2. **`scripts/run_eval.py` is TRIGGER-only and takes a different file.** Its own `--help` says "Run trigger evaluation for a skill description"; `--eval-set` points at a separate flat `[{"query":…, "should_trigger":…}]` set, not `evals.json`. This is the one the Windows `select.select` defect below belongs to. It is not "the runner" — it is one narrow tool. **And its method plants a decoy, which makes it the wrong instrument for comparing siblings.** Read off the source 2026-08-31: it never exercises the installed skill. It writes a throwaway command file at `.claude/commands/<skill>-skill-<uuid8>.md` carrying only the description, runs `claude -p <query> --output-format stream-json --include-partial-messages` from the discovered project root with `CLAUDECODE` stripped from the env, and counts the query as triggered when that decoy is selected. For measuring one description's pull in isolation that is the right shape. For asking whether two sibling descriptions still route apart — `disconfirm-first`'s three, say — the real installed skill competes against its own decoy twin, so a miss is unattributable. Use a plain `claude -p` run instead and read the selection off the transcript (`{"name":"Skill","input":{"skill":"<plugin>:<skill>"}}` — the higher-precision of the two detectors the trigger-harness plan measured). Side effect worth knowing before pointing it at a repo: it creates `.claude/commands/` in whatever project root it finds.
3. **`claude plugin eval` is a third, unrelated thing, and it is gated.** It reads `evals/**/case.yaml` or `prompt.md` + `graders/*.md`, offers `--ablation with-without`, `--runs`, `--threshold`, `--max-cost-usd`, and an HTML report that **publishes to claude.ai by default** (`--no-publish` keeps it local) — but every invocation including `init --bare` returns `` `plugin eval` is currently in early access ``, and no `case.yaml` exists on disk to copy the schema from. Do not author for it blind. **Re-probed 2026-08-31 — still gated, and the way it is still gated is a trap.** The `--help` output has grown a lot since (an `--allow-tools` operator grant, `--mocks`, `--judge-model`, `--case` / `--tag` filters, `--json`, and a `tool_used: Skill` grader described as a plugin-fired indicator under `--ablation with-without` — which is precisely the triggering check this file says we lack). That reads exactly like availability. It is not: `init --bare` in a scratch dir still returns the early-access line. Richer help was mistaken for a lifted gate once already this way, so probe the gate, never the help text.

**What actually blocks running the grading workflow is therefore NOT the format** — it is (a) the phantom-domain prompts in point 3 of the list below, (b) cost, since it executes the skill N times per prompt, and (c) it needs subagents (skill-creator's own Cowork note says the benchmark's baseline comparison "aren't meaningful without subagents"). **This paragraph replaces an earlier version of itself that claimed "no runner reads our format" — that was wrong: it came from collapsing the three tools above into one, and from a `find` that missed skill-creator because the install path contains a hash segment.**

**They have never been executed, and three things block running the trigger eval from this repo on Windows — verified 2026-08-06, do not re-discover them:**

1. **Wrong artifact.** `skill-creator`'s `scripts/run_eval.py` does not read `evals/evals.json`. It wants a separate flat trigger set, `[{"query": ..., "should_trigger": bool}]`. Ours is the qualitative set (prompt / expected_output / assertions), which belongs to the grader workflow instead. A trigger set can be derived: `should_trigger` = the eval has no `skill_not_triggered` assertion.
2. **The runner is Windows-incompatible.** Its read loop gates on `select.select([process.stdout], ...)`; on Windows `select` supports sockets only, so it raises `OSError` WinError 10093, unwinds to `return triggered` with `triggered` still `False`, and reports **every** query as not-triggered. Positives all fail, negatives all pass vacuously — a clean 19/19 + 21/21 split that looks like data and is not. Replace the streaming read with `communicate(timeout=...)` to fix it.
3. **The `test-authoring` prompts name a domain this repo lacks — but read this as an EXECUTION limit, not a prompt defect.** Four of those eval files name a C#/.NET billing domain (`BillingService.CreateInvoice`, `POST /invoices`, `InvoiceConsumer`); run *as executions* the model greps, finds nothing, and correctly declines. **Do not "fix" this by rewriting the prompts to this repo's own subject matter** — that trades unrunnable for *unrepresentative*, and these skills exist for consumer code repos, so a prompt about a Markdown plugin marketplace measures a case no user has. The earlier version of this entry offered that rewrite as a valid option; it is not.

   The census that settles it (2026-08-14, all 7 sets, **82** assertions, 17 kinds — an earlier version of this line said 78, which was simply wrong arithmetic): **`skill_triggered` ×23 + `skill_not_triggered` ×25 = 48 of 82 (59%) need no codebase at all** — they measure which skill Claude *selects*, where a nonexistent class is arguably better than a real one because it cannot pass for the wrong reason. Only ~26 (33%: gate / protocol / delegation / audit / table) need real execution, plus `risks_calibrated` ×4 needing a real artifact. So the phantom domain blocks a third of the value, not all of it.

   **But "needs no codebase" is not "is cheap" — costed 2026-08-14 and this is the binding constraint on the whole trigger tier.** Every probe pays a fixed floor before it measures anything: this file alone is 33,536 bytes ≈ 8.3–8.8k tokens, plus the system prompt, every installed plugin's descriptions, and auto-memory. A full ~46-query sweep is ≈ **400k tokens** single-shot and ≈ **1.2M** at the 3-runs-per-query the comparable tool defaults to, and it must re-run after every description edit — against a benefit ceiling of ~940 tok/session (the six `test-authoring` skill descriptions; the other ~1,270 of its ~2,198 always-on total is *agent* descriptions, which triggering never touches). Break-even sits past 1,500 sessions. So measuring this tier is a **cost decision, not a free win** — see `.claude/plans/backlog/plan-trigger-harness.md`, which is not approved to build for exactly this reason. A small probe set (~8) is the only version whose arithmetic works.

What each tier actually needs: the 59% needs only **lookup-free prompt shapes** (prefer `"add unit tests for the files I just changed"` — Mode A, git-diff scoped — over `"add unit tests for BillingService.CreateInvoice"`, because caveat 4 below counts the first `tool_use` and a phantom target invites an exploratory `Glob` that reads as a miss). The 33% needs a code fixture repo, which is a **separate investment and not currently recommended** — five of six `test-authoring` skills have already executed in real consumer repos under the current architecture, which is stronger evidence of "does it work" than a synthetic fixture; a fixture buys *repeatability* (a regression gate), not first proof. **`review-plan-risk` is the exception and the natural pilot**: 0 of its 12 entries mention that domain, its subject *is* design artifacts, and this repo is made of them — but note it **auto-fixes what it reviews**, so point it at a few deliberately-flawed throwaway markdown artifacts (which also gives a known-answer case), never at live skill files across 12 × N runs.

A fourth, milder caveat: the runner counts the **first** `tool_use`, so any exploratory `Glob`/`Grep` before the skill is selected reads as not-triggered. A skill whose own first step is "locate the artifact" (e.g. `review-plan-risk`) will look like a miss even when it behaves correctly.

## Measuring anything (tools we build to check our own work)

**A measurement tool gets checked harder than the thing it measures.** Its output carries the authority of "this was measured", so a wrong number does not just fail — it launders a false conclusion into a decision. Several instruments built here were wrong on their first version and three of those shipped: the dashboard's token count accumulated `usage` **per record with no `message.id` de-duplication**, and read only `input_tokens` / `output_tokens` while ignoring `cache_read_input_tokens` and `cache_creation_input_tokens` entirely — **both halves fixed in `d00c05f`**, which de-duplicates on `(file, message.id)`, reports the cache figures as their own third number, and is pinned by `tests/selfcheck.py`'s `test_token_totals` (six mutations, each verified to turn the suite red, the mutation itself verified to be no no-op); the skill-eval runner reported a clean 19/19 + 21/21 split that was `select.select` failing on Windows; and `resolve-issue/SKILL.md` carried a cost anchor that was ~4.3× too high (withdrawn in `a8f3a53` — the line is gone, so do not go looking for it). (That is not a base rate — an instrument that was right first time leaves no debugging trace, so it cannot enter the denominator. It says only that the failure is common enough to need a process rather than care.)

Three rules, in order:

1. **Every check needs a known-answer case that makes it fail — and run it BEFORE the correctness review, not after.** A check that has only ever been run against good input has not been tested. More than that: a review reads a check for whether it is well *built*, and cannot tell you whether it will ever *fire*. Verified here (2026-08-10): a guard survived three `review-plan-risk` passes and two fix rounds, and then its first known-answer case showed it never triggers on the input class it exists for — the premise under it ("a thin ticket yields zero load-bearing claims") was false, because an LLM asked to enumerate claims from vague text invents them instead of returning an empty set. No amount of reading the guard finds that. Fifteen minutes of fixture did. **Treat the fixture as the thing that decides whether to build, not as acceptance work afterwards.**
2. **Mutation-test the check set**: delete any one check and the known-answer set must go red. A check that can be deleted without turning the suite red does not exist. This is not hypothetical — an audit tool here passed 4/4 with two of its five checks stubbed out. (A companion example once cited here — "a self-check case had frozen a bug in place" — was withdrawn: on inspection the case was pinning *correct* semantics, and "fixing" it would have weakened the only check that catches a leaked read.)
3. **No result is quotable until 1 and 2 hold.** State the limit instead ("the tool has not been validated"), the same voiced-limit discipline the review skills use.

**Rules 1 and 2 apply to a borrowed instrument too, and the one we borrowed was broken.** `skills-ref` — the Agent Skills spec's own reference validator, from `agentskills/agentskills` — reads `SKILL.md` with `Path.read_text()` and no `encoding=` (`parser.py:89`, `validator.py:172`), so on a cp1252 Windows locale it decodes UTF-8 as one character per **byte** and its 1,024-character description check counts bytes instead. Every em-dash costs 2 phantom characters, an accented letter 1, an emoji 3. Measured with a repro of two descriptions each exactly 1,024 characters long: the all-ASCII one passes, the one made of em-dashes is rejected as **2,992 chars**. Prefix the command with **`PYTHONUTF8=1`** and the same file passes — that is the workaround, and it is also the confirmation of the cause. Three things follow. The failure is one-directional, so it manufactures false failures and never hides a real overage. It is platform-split — the same skill passes on a UTF-8 locale — so a Linux CI run would never surface it and only a Windows contributor sees it. And it was found only because the validator was pointed at a known-bad input first (rule 1) rather than trusted on a clean 14/14: a pass from an instrument that has never been made to fail is not evidence. Current exposure here is nil but thin — the longest real description is `resolve-pr-comments` at 997, which the inflated count puts at 1,005, leaving about nine more em-dashes of room against a house prose style that is full of them.

**A measurement can justify a *concern* without justifying an *instruction* — so mutation-test the instruction, not the observation.** This is the same trap one level up, and it was walked into during the very session that added rules 1 and 2 to a skill. Nine uncontaminated repositories were sampled: 32 of 161 pull request titles began with a bracketed word, and exactly one of those brackets held a ticket reference — the rest were component tags. A true, useful, hard-won number. It was then written into the skill as a rule ("a bracketed word is far more often a component tag than a ticket reference, so do not put a ticket key there"). Removing that clause and re-running the fixture changed nothing, in two cells — including one where the sample was anonymised so no prior knowledge of the project could help. The executor derives it from the sample structurally every time: the tags are words rather than ids, the same tag recurs across pull requests where a per-change key could not, and the tags reappear in bodies as code units. The measurement was real and the instruction was dead weight, competing for attention with the rules that do fire.

So the question a measurement answers is "is there something here to get wrong?", never "does the artifact need a line about it?". Only the second question ships text, and only a fixture answers it. Prefer *enabling* the executor to see the thing — carrying an author field through a format string, say — over *telling* it what to conclude: data cannot misfire, and a rule that duplicates the executor's own reasoning is indistinguishable from one that is simply wrong until you test it.

**Reading Claude Code transcripts — two traps that have already bitten.** Each is verified in this repo, do not re-derive them:

- **`usage` is repeated, tool calls are not.** One API response is written as several `assistant` records — one per content block — and *every* record repeats the same `message.usage`. So summing usage per record multiplies each figure by however many blocks that response held. **That block count differs per response, which is the whole point: there is no inflation ratio to measure once and divide by afterwards** — the repeats have to be dropped as they are read, by de-duplicating on `message.id`. (Do not quote a measured multiple as if it were that ratio. One was recorded here for months and it was a property of one session's content mix, not of the format.) Tool calls need no such care — `tool_use` blocks are written once each, so counts never inherit the inflation, which is why a count is the safer basis for comparison than any token sum. **And "ids are unique" is not an invariant**: across the corpus a number of ids appear more than once, nearly always across different files. **Pair a `tool_use` to its `tool_result` on `(source file, id)`, never on `id` alone** — and key any usage de-duplication on that same pair, for the same reason.
- **A whole session expires together, and a resume reprieves all of it.** Cleanup keys on the **top-level session file's `mtime`**, default **30 days** (`~/.claude/.last-cleanup` records the last run), and it removes the session **together with its `subagents/` directory** — subagent files are not separately retained. Touching a session resets its mtime and spares the entire bundle, so **file age is not evidence of the retention rule**. Evidence (2026-08-07): subagent mtimes cluster at 0–30 days, then a completely empty band from 31 to 43 days, then 14 `agent-*.jsonl` at 44–45 days whose two parent sessions were resumed 3.2 days ago; 0 orphans across 32 subagent directories, in a corpus 129+ days old. **Read that evidence with its limit:** no top-level session older than 30 days survives anywhere, so "zero orphans" is consistent both with "the directory is deleted with its parent" and with "those sessions simply had no subagents". The empty 31–43 band is the load-bearing part; the deletion mechanism itself is inferred, not observed. Plan any transcript-based audit against **30 days from the session's last activity**.

  This one question has now been answered wrongly three times, each way: first a cliff "found" by scanning `find -mtime +28` (a filtered subset cannot establish where a distribution ends — it manufactures the edge it reports); then an over-correction declaring the question unknowable when ten minutes of measurement settles it; then a backwards model built by reading subagent mtimes as exemption instead of as reprieve. **`mtime` is last-append, not creation — it bounds retention but says nothing about content age**, and a resumed session carries months-old records under a recent mtime.

Beyond that: `input_tokens` counts only the cache-miss delta once prompt caching is on, so it is not "the input size"; and a per-step window contains whatever the human did during it (one measured step window spent ~47 minutes on an unrelated ticket), so per-step figures are upper bounds on pipeline work, never measurements of it.

## resolve-issue-dashboard

The only executable code lives under `plugins/issue-to-pr-pipeline/skills/resolve-issue-dashboard/`: `scripts/{serve_progress.py,parse_session.py}` — a read-only, localhost-only observer that tails Claude Code transcripts and `.claude/resolve/<ticket>/state.md` (plus the run's append-only `timings.md`, for per-step durations) to visualise a `resolve-issue` run (it never writes to transcripts or `.claude/resolve/`) — plus `tests/selfcheck.py`, a stdlib deterministic self-check of the parser's pure logic. Run the dashboard: `python serve_progress.py [--cwd PATH] [--ticket TICKET] [--port N] [--no-browser]`; run the checks: `python tests/selfcheck.py`.

**Where the screen's data comes from.** Most of it is *not* `state.md`. That file supplies the ticket, the cursor, the branches, `plan-approved`, `pr-url`, `attention`, and `started`/`ended`; `timings.md` supplies the per-step durations and the `×N` re-entry count. Everything else is derived from the Claude Code **transcript** — `~/.claude/projects/<encoded-cwd>/<session>.jsonl` and that session's `<session>/subagents/agent-*.jsonl`: the agent-activity feed, the token and tool-call totals, the session id in the header, whether the run reads as running or parked, and (via each transcript's `cwd`) the cross-repo run list in the left panel. Worth knowing before debugging a blank panel — and it is why a fixture built from the two Markdown files alone renders an empty feed, zero counters, a single repo, and an idle status.

**Transcript record shape.** Claude Code does not document it, so this was read off `Collector._parse_line`; you need it whenever you synthesise a transcript, e.g. to rebuild the README screenshot after a pipeline change. One JSON object per line. Only `type` `"user"` and `"assistant"` are parsed — everything else is skipped silently. Tokens come from `message.usage.{input_tokens,output_tokens}`. Tool events come from `tool_use` blocks in `message.content[]`, and a tool's duration from pairing its `tool_use.id` with the later `tool_result.tool_use_id`. A main-session assistant record whose `stop_reason` is `"tool_use"` is what marks the session as still working; any other stop reads as yielded to the human, which is what flips the run from running to parked. The top-level `cwd` field is how a project dir is mapped back to its repo.

## Conventions

- Commits: plain `<summary>` (≤50 chars), no ticket prefix; commit to `main`; no `Co-Authored-By`.
- **This repo is public.** Nothing that reaches the remote may carry internal detail — no ticket ids in commit subjects, bodies, **or branch names**, and no internal host or repo names. Skill prose uses `acme-…` as the placeholder ticket format. Grep a diff before committing.
- Prose in skills/docs uses semantic line breaks (break at clause boundaries), except rendered Markdown like READMEs (one line per paragraph). See the user's global CLAUDE.md for the full prose/comment style rules.
