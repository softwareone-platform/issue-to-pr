# Review passes — `b-security-review`, `b-code-risk`

Cluster reference for `resolve-issue`'s two Phase B review steps. **Load this before executing either of these steps** — a straight run loads it before `b-security-review`, but a resume can land the cursor directly on `b-code-risk`, and each must load this file first too. These two steps share the `apply → verify → commit` discipline and the verify-subagent below; that shared context is why they live in one file. The spine (SKILL.md) owns the transitions between them, the `attention` set/clear rule, the commit-message format, `plan.md`-as-oracle, and the loud `SECURITY REVIEW DID NOT RUN` surfacing at the `b-code-risk`→`b-open-pr` checkpoint — this file points up to those rather than restating them.

**Two within-cluster variations — do NOT present the two steps uniformly:**
- **Preflight binds only `b-security-review`.** The R4-bis built-in-shadow preflight guards `b-security-review` (it invokes the bare-name built-in `security-review`). `b-code-risk` invokes the plugin skill `/disconfirm-first:review-code-risk` — no bare-name shadow risk — so it has **no** preflight.
- **The verify-subagent is a guaranteed gate for one, a backstop for the other.** For `b-security-review` the verify-subagent is the pipeline's **guaranteed** build+test gate for its edits (it withholds the commit if it cannot run) — but only **when that pass changed code**; a pass that changed nothing commits nothing and runs no gate. `review-code-risk`'s own verifier at `b-code-risk` is only a **backstop**, because it spawns a verifier *only when it auto-fixed something*. So on the path where `b-security-review` changed nothing and `b-code-risk` auto-fixed nothing, no Phase B review gate runs at all — the standing regression oracle is then the tests `b-write-tests` committed (green when it closed). Do not narrate the pipeline as if a review-pass gate always runs before every PR.

## Shared per-step discipline (each: apply → verify → commit)

`b-security-review` runs after `b-write-tests` has committed the tests and before the fix review (`b-code-risk`), and follows a per-step discipline so a resume always finds a clean, committed tree: (1) ensure the working tree is clean — `git restore` any stray uncommitted edits an interrupted prior run left, so re-running the step is idempotent; (2) run the review and apply its accepted fixes to the **working tree, uncommitted**; (3) if the step changed nothing, commit nothing and advance (the prior step's verification still stands); (4) if it changed code, spawn a fresh **verify-subagent** — read-only, its own context — to run `build` and the affected tests (selected from the *changed* files, falling back to the suite when selection is unclear; not only `b-write-tests`'s set) and return a structured `pass` / `regression` / `stale` / `env` classification. If the verify-subagent cannot run at all — no build/test command can be established, or a subagent cannot be spawned — do **not** commit the change unverified and do **not** skip silently: surface it as a voiced limit (never silently assume the gate ran — the principle `review-code-risk`'s verifier follows with no command; but because this is the *guaranteed* gate, not a backstop, it **withholds the commit** rather than proceeding on a static read), then treat it like an `env` red — the human may explicitly accept and let CI verify, or the step waits (`attention`). That verify-subagent is the pipeline's **guaranteed** build+test gate for these edits (when it changed code); `review-code-risk`'s own verifier at `b-code-risk` is only a backstop, because it runs *only when it auto-fixes something*. (5) On `pass`, let the human glance at the `git diff`, then commit that step's batch — staging only the files it touched, `acme-…` message, and no AI co-author trailer unless the run was explicitly opted in (per b-implement) — and advance. Each is a **conditional checkpoint**: clean/green auto-advances with no human stop; only a red verification or an undispositioned blocking finding pauses the run — set `attention` with a step-specific reason (per its rule in SKILL.md's `state.md` field).

## Handling a red verify-subagent — compose existing skills, never game a test green

`env` / flaky → re-run once; if still environmental, the human may **explicitly accept** it and open the PR so CI verifies in the real environment (record that acceptance — it is the *only* way a red result reaches a PR). A real red is never shipped and is never "fixed" by weakening a test. Route by classification: a **review-pass fix that itself regressed** (a still-uncommitted fix `b-security-review` or `b-code-risk` just applied) → `git restore` that still-uncommitted fix and re-verify; a **stale pre-existing test** (a security fix intentionally changed behaviour) → the stale-vs-regression call is made by the independent verify-subagent, never by whoever wrote the fix (add a human confirm for security-related reds), then delegate `/test-authoring:update-*-test` — which brings its own writer and independent verifier — to update the test, then re-run the verify-subagent once (bounded, no loop); a **security fix that itself needs real rework** → the human directs fix / defer / back-out. `resolve-issue` may invoke `update-*-test` here because it is the orchestrator — unlike `review-code-risk`, which may only recommend a hand-off.

## `b-security-review` — review code security

Invoke the built-in `/security-review`. It is report-only — it scans the committed branch diff and emits a findings report, and does **not** modify code. Disposition each finding under the **blast-radius policy**, the same anchor rule `review-code-risk` uses: a flaw this change *introduced*, or an in-anchor flaw (inside the changed files), is fixed now; an **out-of-anchor** finding (needing changes beyond the change set) is **never silently folded into this PR** — surface it and let the human pick, per finding: fix now (accept the wider scope), or **draft a follow-up ticket's title and description** for the human to file (do **not** auto-create it — this pipeline does not create tickets itself), or record an explicit risk-acceptance. A **high-severity** out-of-anchor security finding defaults to pausing (`attention`) — it is never shipped silently. Apply the accepted fixes through the per-step discipline above; for any accepted fix that **adds behaviour beyond the plan** (security fixes especially, in- or out-of-anchor), write a one-line record into `plan.md` (e.g. `Approved during security review: <what> — expands scope; tests updated accordingly`) before `b-code-risk`, so `review-code-risk` aligns the diff against the true, expanded intent instead of flagging it as an undocumented expansion. **Preflight (R4-bis) — here a shadow is worse than an absence.** Confirm the responder behaved as the native prompt-based reviewer — an inline, report-only findings pass over the committed diff with no external call — not a shadowing plugin that asks to install a CLI or sends the diff away (the shadow mechanism is in SKILL.md's **Invocation discipline**). A shadowed `security-review` must **never be silently accepted** — a wrong tool that merely *answered* would suppress the loud absence signal and leave the pipeline's only built-in review pass silently unrun. So route every case that is not a positively-confirmed native run — unavailable, not behaving as the built-in, or one you **cannot positively confirm** — the same way: treat security review as **not having run**. **Write the fact into `plan.md` before advancing the cursor** — a line beginning exactly `SECURITY REVIEW DID NOT RUN` followed by which case it was (unavailable / shadowed / could not confirm). Use the same append mechanism as the scope-expansion record above. This is the *record*; the checkpoint and the done summary are the *display*, and both read it from there. Persisting it is what makes the signal survive: the cursor advances past `b-security-review`, and a run resumed in a later session has no memory of this step — without the written line the pipeline would open a PR believing security was covered, and nothing on disk would contradict it. (Restore the built-in by disabling the shadowing plugin — README prerequisite.)

## `b-code-risk` — review the fix

First `git fetch origin` so `git merge-base origin/<base> HEAD` is not stale. Then invoke `/disconfirm-first:review-code-risk` with its anchor triple — the committed diff, the issue, and `plan.md` (which it reads from disk). By now `plan.md` may carry any `b-security-review` approved-scope records, so `review-code-risk` aligns against the accurate, expanded intent rather than flagging those as undocumented expansions. It auto-fixes real risks inside the changed files and its verifier re-runs build and the affected tests — a **backstop** when `b-security-review` already ran the guaranteed build+test gate (i.e. when it changed code); if no prior pass changed code, the committed `b-write-tests` tests are the standing oracle and this verifier (which runs only when `review-code-risk` auto-fixed something) is the sole post-review gate. Its own auto-fixes land **uncommitted** (so the human keeps the `git restore` escape hatch); commit that batch — staging only the files `review-code-risk` modified — only after the skill returns and the human has seen its result table. If there were no auto-fixes, `b-code-risk` commits nothing. Test-adequacy gaps it hands back to `test-authoring` are a recommendation surfaced to the human, not an auto-invocation.

**Behavioural symptom re-check (`b-code-risk`'s last action).** Green tests are necessary, not sufficient — they can pass while the original symptom persists. As the final action of `b-code-risk`, before the checkpoint (in SKILL.md), confirm the symptom (per the reproduction recipe in `plan.md`'s Verification / Acceptance section) no longer reproduces by driving the affected flow end-to-end and observing the behaviour. Apply this principle **inline, with the tools already in hand** — do **not** add a hard dependency on a `/verify` skill or any component this plugin does not already declare (the invocation discipline in SKILL.md). Skip only when the change has no runtime surface to drive. Fold the outcome into what the checkpoint presents: a symptom that still reproduces is a pre-PR blocker, surfaced like an unresolved risk — the checkpoint stays a human-disposition gate, now with the behavioural result as one of its inputs.
