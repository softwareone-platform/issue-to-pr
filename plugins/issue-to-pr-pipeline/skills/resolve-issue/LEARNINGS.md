# Generic-learnings loop — mechanics and rationale

Disclosed reference for `resolve-issue`'s generic-learnings machinery: loading honored conventions (preamble P5), capturing candidates (the cross-cutting capture step), and the done-step harvest upkeep. Each inline site keeps its decision; this file holds the detail and rationale.

(`resolve-issue-learnings` reads this file as part of its oracle set — it globs the resolve-issue skill directory — so behaviour described here stays visible to the learnings verifier.)

## Loading honored conventions (preamble P5)

Read `$HOME/.claude/resolve-learnings/conventions.md` if it exists and honor its preferences for the rest of this run **when they are consistent with the current behaviour** — they are honored preferences, not hard rules, so a preference that no longer fits simply does not apply. The preferences cover resolve-issue's own surface (gate flow, sequencing, state, the a-draft-plan step, component-choice); one that names a delegated component's internals is not honorable here and is simply skipped. Skip in memory any entry past its `ttl`; and if the file's top-line `schema_version` marker is one this run does not recognise, honor nothing from the file (that marker is **per-file, not per-entry**). **Do not write the file** — the read is read-only because a concurrent run shares this one user-global file, and the physical prune of stale entries belongs to `/resolve-issue-learnings` (the single writer). The read is **non-fatal**: if the file is absent, unreadable, half-written, or unparseable, honor zero conventions and carry on — a learning store must never block or break a run. These conventions are the *generic* lessons harvested from past runs; capturing new ones is the cross-cutting step below, and turning candidates into honored conventions is the separate `/resolve-issue-learnings` skill.

## Capturing generic learnings (cross-cutting, best-effort)

Throughout the run, quietly capture *generic* observations about the pipeline itself — its gate flow, step sequencing, state handling, or how it chains the component skills — so they can later be verified and fed back by `/resolve-issue-learnings`. This is **capture only**: nothing here is trusted or applied until that separate skill verifies it against the current skill as ground truth.

**Bias to silence — the default is to write nothing.** Append a candidate only when an observation is all of: *generic and orchestration-scoped* — it is about **resolve-issue's own controllable surface** (its gate flow, step sequencing, state handling, how it drafts `plan.md` in a-draft-plan, or which component / test type it chooses to invoke) and would hold in any repo running this pipeline; a learning about the *internal* behaviour of a delegated component (how a test is written, what goes in a PR body, how a risk is judged) is **out of scope here** — resolve-issue only invokes those components and cannot honor a convention about their internals, so such a learning belongs to that component's own loop, and a repo-specific convention belongs to that repo's own local conventions, not here; *grounded* in a concrete signal (a specific gate interaction, a `SKILL.md` instruction that misfired, a verdict that was wrong) — never a vague feeling; and *novel* (not already obvious, and not already a known convention). Most step boundaries produce nothing notable, and capturing nothing is the normal, healthy outcome — over-capturing floods the store with noise and defeats the loop.

**When and where.** At each step boundary — the same point P4 already writes the next step into `state.md` — take one beat and ask: *did anything about the pipeline itself misfire, surprise me, or prove awkward this step?* Usually the answer is no, so append nothing and move on — that explicit per-boundary check is what makes the rare real observation actually get caught rather than passed over, without lowering the silence bar. Only when the answer is yes **and** it clears the bar above, append it to the user-global dead-drop `$HOME/.claude/resolve-learnings/candidates.md` (create the directory and file if absent), in the entry shape `/resolve-issue-learnings` documents (observation, evidence, origin-step, run) — that skill's format is the single source for the entry shape, so the captured entry and the harvested entry never drift. Append with a true append (`>>`), not a read-rewrite, so concurrent runs in other repos do not clobber the file. Capturing per step rather than only at `done` is about *timing* — a long run's early observations would otherwise be lost to context compaction before the end — not volume; the silence bar still applies at every step.

**It is a dead-drop, kept off every hot path.** The candidate file is **user-global** (`$HOME/.claude/...`), deliberately **not** the target repo's `.claude/` (which is repo-specific ground), **not** `state.md` (so it never perturbs the resume cursor or the dashboard's parsing of it), and **not** any auto-recalled memory index (an unverified, sample-of-one candidate must not influence a future run before it is verified). Appending is **append-only, silent, and non-fatal**: ask the human nothing, add no gate, and if the write fails just note it in one line and continue — capture must never block the pipeline (the same posture as P1 and P5).

## Self-improvement upkeep (done step)

Count the **fresh** generic-learning candidates in `$HOME/.claude/resolve-learnings/candidates.md` — *fresh* meaning entries that do **not** carry a `deferred:` marker (that marker is added by an earlier unattended harvest to the ones it could not machine-decide; `/resolve-issue-learnings` defines the entry format). If that count is at or above a small threshold (default 5) and this is an interactive run, auto-invoke `/resolve-issue-learnings` in its **unattended** mode (pass the `unattended` argument) so the captured learnings are verified and the high-confidence ones applied to your conventions without you having to remember to run it — this is resolve-issue's own internal upkeep, not a user step, so there is no gate. Counting only the *fresh* (non-`deferred`) entries is also the natural snooze: an unattended pass either archives a candidate (confirmed / refuted) or marks it `deferred`, so right afterwards the fresh count is ~0 and it will not re-fire until new captures accumulate — no separate snooze state is needed. It is **non-fatal** (any failure to count or invoke prints one line and is skipped — it must never block `done`) and **skipped in a non-interactive run**. The unattended harvest never proposes `SKILL.md` edits (mode Y) and never auto-applies borderline learnings — it defers those; if it deferred any, note in one line that a manual `/resolve-issue-learnings` pass would clear them.

## What the done summary must affirm about capture

The `done` result summary's one-line self-improvement report must **affirm the capture mechanism ran this run and state how many generic-learning candidates it captured** — so a `0` reads as a *confirmed* "nothing notable this run", not an ambiguous silence (a capture that actually *failed* is the distinct, loud signal: it surfaced its own one-line note when it happened, per the capture section above) — plus the upkeep step's harvest outcome (applied / deferred). The per-boundary capture check is therefore deliberately **not** silenced: its failures stay loud inline, and the `done` report is the positive confirmation that lets `0` mean "genuinely nothing" rather than "did not run".
