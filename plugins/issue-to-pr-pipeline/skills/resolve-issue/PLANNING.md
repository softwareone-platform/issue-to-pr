# Planning cluster — `a-fact-check`, `a-elicit-decisions`, `a-draft-plan`, `a-harden-plan`

Cluster reference for `resolve-issue`'s Phase A authoring steps. **Load this before executing any of these steps** — a straight run loads it before `a-fact-check`, but a resume or a gate-revise re-entry can land the cursor directly on `a-elicit-decisions`, `a-draft-plan`, or `a-harden-plan`, and each must load this file first too. These steps share the `decisions.md` / `plan.md` authoring flow and the revise loop, which is why they live in one file. The plan-approval gate — `a-gate-approve` — is **not** here: it lives in the spine (SKILL.md), because it is the Phase A→B pivot. But when a gate revise **invalidates a decision**, the spine routes back into these steps; the "Re-entry from a gate revise" note at the end owns that behaviour. The spine owns `decisions.md`'s resume-state contract (the sentinel / `resolved` / `open` semantics the staleness gate reads); this file owns only how these steps *author* it.

## `a-fact-check` — fact-check the issue

`a-fact-check` is the pipeline's first step and runs only after the full preamble (P0–P5) has completed — on an interactive run that includes P1's dashboard launch; never enter `a-fact-check` directly from P4's `state.md` write. Invoke `/disconfirm-first:review-issue-fact` on the issue. Its HALT / PROCEED / RESOLVE verdict is **advisory**, not a hard stop (it is designed to run unattended inside this orchestrator). Surface the verdict; on HALT (a refuted load-bearing claim) or RESOLVE, name what is wrong or missing and ask the human whether to stop and resolve it or proceed anyway — default toward stopping, but the human decides. **Four things produce RESOLVE, and the ask differs by which** — read the verdict rather than assuming: the load-bearing set came out **empty** (nothing in the issue was a claim a fix would depend on), a load-bearing claim's verdict is **`needs-info`**, or its Verifier is **`disputed`** or **`not-verified`** (the component reads both of those as `needs-info`). An empty set asks for a testable failure path or repro; a cross-repo or runtime-only `needs-info` asks for the repo to be checked out or the runtime check run; `not-verified` means no independent agent read the verdict at all, so nothing was corroborated. `review-issue-fact`'s own rollup rules are the authoritative list — this enumeration follows them and must be re-checked against them if they change. On PROCEED, continue to `a-elicit-decisions`. It writes `fact-check.md` itself.

## `a-elicit-decisions` — resolve open decisions (decision elicitation)

Before `a-draft-plan` drafts anything, settle the **design decisions the plan will rest on** — the choices the issue leaves open — so `a-draft-plan` drafts from resolved decisions, not guesses. Split what you face: a **fact** has a single answer discoverable in the code, config, docs, or via a tool (which file, current behaviour, whether a method exists, which setting governs X) — **look it up yourself; never ask the human, and do not assume `a-fact-check` gathered it** (`a-fact-check` only fact-checks the *issue's* claims, not the plan-drafting facts). A **decision** is a product or design choice the code cannot settle, with more than one defensible answer, **that changes the shape or scope of the fix** (load-bearing); a choice that is both a look-up and a preference counts as a decision only when it changes the fix's shape or scope, else take the code-consistent default and note it. Enumerate only the load-bearing decisions — do **not** manufacture them. **If there are none, this step is a voiced no-op:** record `none — the ticket specifies <what makes it sufficient>` in `.claude/resolve/<ticket>/decisions.md` (so a thin ticket cannot pass by silently self-declaring), and continue to `a-draft-plan`. Otherwise ask them **one at a time, each with your recommended answer and a one-line why**, as end-of-turn prose — never an `AskUserQuestion` picker (the rule `a-gate-approve` follows) — looping until the load-bearing decisions are settled. Record every decision in `decisions.md`, each marked `resolved` or `open`. **`a-elicit-decisions` does not create `plan.md`** — `a-draft-plan` remains its sole author, so the staleness gate's *plan.md-absent = fresh* invariant holds. Write `next-step: a-elicit-decisions` while the loop is open; on resume, re-present the `open` entries from `decisions.md`. **Degradation:** in a non-interactive run the decisions cannot be asked — record `skipped (non-interactive)` in `decisions.md`, voice it, and let `a-draft-plan` draft on best inference.

## `a-draft-plan` — draft the plan

Draft the design for the fix into `.claude/resolve/<ticket>/plan.md`. `a-draft-plan` is the **sole author** of `plan.md`: first fold every `resolved` entry from `decisions.md` (if `a-elicit-decisions` wrote any) into the plan as stated premises, then draft the rest. **Read `.claude/resolve/<ticket>/fact-check.md` before drafting, and take its per-claim verdicts as drafting input — not only its overall recommendation.** A design must not rest on a claim the codebase **refuted**: name it in the plan as an unsettled premise, or design around it, but never draft over it as though it held. Treat a load-bearing claim left at **`needs-info`** the same way — say what evidence is missing rather than assuming an answer. **And establish that the change set the issue implies is non-empty before drafting around it.** An issue states a symptom and usually implies a target — the members with no consumers, the callers still on the old path, the setting nobody reads — and that implication is a *checkable claim about the current codebase*, not a given: enumerate the target set here, against the code, by the criterion the issue itself uses, and name what you found. **If the set comes out empty, say so and do not draft a change around it** — record the enumeration and its criterion as the plan's finding, and put the ticket's disposition to the human as the decision it is (close as no-change, redirect to whatever the enumeration did surface, or correct the criterion), rather than picking a target that satisfies a criterion nobody set. Include the enumeration whatever it returns, because a non-empty result is the evidence the rest of the plan rests on. This belongs here rather than in hardening for two reasons that are properties of the pipeline, not of whoever drafts: `review-plan-risk`'s ground-truth premise pass is its Step 2, two steps downstream, so a plan drawing its target from the issue alone makes its central commitment before anything can refute it; and an empty target set has no terminal of its own — the `RESOLVE` verdict above covers four states of the *fact-check*, none of them "the premises hold and the work turns out to be nothing". The plan is rendered in full at `a-gate-approve`, so naming it there is what puts it in front of the human. Read the file if present, degrade if absent (a resume can land on this step with no such file) — never block on it. Without this, a refuted claim reaches the plan unchallenged and comes back two steps later as a risk `review-plan-risk` has to re-derive from the same evidence. Open the file with a short **Summary / Highlights** section — a few lines giving the root cause, the fix approach, and the verification oracle — so the human can orient at a glance before the detail. This leading summary is part of the plan (hardened in `a-harden-plan`, rendered with the full plan at `a-gate-approve`), not a separately generated blurb. Keep it in sync with the body: whenever the plan body changes — `a-harden-plan`'s in-place auto-fixes or any `a-gate-approve` revise-loop edit — refresh the summary to match, and on any conflict the body wins, because a stale summary leading the plan would let the human approve a plan they misread. The issue states the *symptom*, never the *oracle* — how we decide the result is right — so the plan must supply it. Include a **"Verification / Acceptance"** section, phrased independently of the fix implementation, that answers three things:

1. the concrete correctness oracle — the observable output, behaviour, or invariant that defines "right", not merely "the bug is gone"
2. which oracle layer it uses, and why that is the strongest one available: **ground truth** (a known-correct value or spec) > **differential** (compare against a reference path, a sibling code path, or the pre-regression behaviour) > **metamorphic** (an invariant that must hold when the exact right output is unknown — round-trip, idempotency, ordering-independence, conservation) > **human judgment** (last resort, and it must be gated)
3. how to reproduce the original symptom, and how to confirm it no longer reproduces
4. that every oracle names a seam **reachable under this plan's own declared constraints** — where the plan's Out of Scope, Testing approach, or a stated design boundary rules out the layer an oracle has to assert at (that project gets no new reference, that component is deliberately untouched, no new dependency), the oracle is unwritable as stated however well it is phrased. There are three ways out and no fourth: **relax the constraint**, **sink the asserted logic down to a layer the constraint leaves reachable**, or **state in the plan that this condition is not tested, and why**. Leaving the conflict unresolved is the one option that is not available, because it does not stay unresolved: `b-write-tests` meets it at implementation with a test that has to compile, and the cheapest resolution available there is a test that supplies its own value and asserts it — which passes, reports done, and tests nothing. This is distinct from the "do not pin a seam that does not yet exist" rule under Testing approach below: that one is about a seam the fix will create, this one about a seam the plan itself has put out of reach.

This section rides through `a-harden-plan` hardening and the `a-gate-approve` approval with the rest of the plan — the oracle is now one of the plan's load-bearing premises `review-plan-risk` pressure-tests, so it must be one the fix cannot cheaply satisfy (the `b-write-tests` discrimination check enforces that).

Also include two more sections:

- **Out of Scope** — the related work this change deliberately does not do. `review-code-risk` reads `plan.md` as its intent oracle in Phase B, so a named out-of-scope list gives it (and the human at `a-gate-approve`) an explicit boundary to judge scope creep against.
- **Testing approach** — the intended test **type** (unit / integration), and — only if an existing seam already exercises the behaviour — that seam; otherwise say the surface is new and `b-write-tests` picks the seam at implementation. Do not pin a seam that does not yet exist. Keep it consistent with Verification / Acceptance; on any conflict the **oracle wins** (the summary/body rule again).

## `a-harden-plan` — harden the plan

`plan.md` is deliberately untracked (see SKILL.md's git-handling note), so `review-plan-risk`'s auto-fix has no git baseline — hand it a **baseline copy** instead. First snapshot the current `plan.md` to `.claude/resolve/<ticket>/plan.baseline.md`, but **only if that snapshot does not already exist** — if it does, `a-harden-plan` was re-entered, so reuse it untouched, so a half-fixed `plan.md` can never overwrite the true pre-fix baseline (the write-once discipline used for `started`). **Every re-entry reached while the cursor is still `a-harden-plan` reuses it**, and an interruption is only one such case: a revise the human gives mid-step, that has you re-draft and re-review, is another — the plan being legitimately better is not a reason to re-baseline it, because the copy's whole value is that it is the text before *any* hardening this cursor visit applied. Then invoke `/disconfirm-first:review-plan-risk` on `plan.md`, **naming that baseline-copy path in the invocation** so it treats the untracked plan as recoverable and auto-fixes it in place rather than degrading to proposed-only. It auto-fixes the real risks in the plan text, runs its own independent verifier, and offers any eligible edge-case risks as its own opt-in batch — the orchestrator does **not** re-implement any of that; it only owns the snapshot. Its edits stay in the working tree with `plan.md` — they are not committed here. Delete `plan.baseline.md` only when the cursor actually moves **off** `a-harden-plan` to `a-gate-approve`. **A completed `review-plan-risk` invocation is not the cursor advancing** — so a mid-step revise keeps the existing copy, and only a re-entry arriving later *from* `a-gate-approve` re-snapshots the current, legitimately-changed plan. Re-taking the copy between rounds leaves the undo able to restore only a half-hardened plan, and it silently costs the one comparison that shows a plan growing across rounds while its scope shrinks.

## Re-entry from a gate revise (invoked by `a-gate-approve` in the spine)

When `a-gate-approve` takes a **substantive** revise that **invalidates a decision** recorded in `decisions.md`, the spine marks that decision `open` and routes back here. Re-entry is targeted, not a fresh Phase A:

- `a-elicit-decisions` re-presents the `open` entries and re-asks **only that one** decision, not every settled one.
- `a-draft-plan` **re-folds only that decision** into the existing `plan.md` — a targeted patch of the affected section, not a fresh full re-draft. `a-draft-plan`'s sole-authorship is the *initial* draft; the re-fold preserves the `a-gate-approve` edit and `a-harden-plan`'s hardening.
- `a-harden-plan` re-runs `review-plan-risk` (the risk surface changed), then the spine re-presents the full plan at `a-gate-approve`.
