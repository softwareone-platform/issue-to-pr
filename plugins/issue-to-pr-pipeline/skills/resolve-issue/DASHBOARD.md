# Dashboard launch (preamble P1) — mechanics and rationale

Disclosed reference for `resolve-issue` preamble P1. The inline P1 keeps the decision (invoke — a required attempt on an interactive run — fire-and-return, outcome non-fatal, idempotent, skip non-interactive); this file holds the rationale. Read only if the dashboard launch behaves unexpectedly.

Invoke `/resolve-issue-dashboard` so the human can watch this run without launching it by hand — delegate the whole launch to that skill (its Python preflight, its singleton `/health` plus version-replace check, its background start) rather than re-implementing any of it here, so there stays one source of truth for how the server comes up. Treat the delegation as a fire-and-return side step: whichever outcome that skill reaches — a server started, an already-running one reused, or could-not-launch — control returns here and the preamble continues (P2 onward) — the cursor is resolved later, at P4, and this run surfaces in the dashboard the moment P4 writes `state.md` — so the dashboard skill's own closing instruction to *stop* ends only the launch sub-task and never the `resolve-issue` run. Performing the launch is a required preamble action on an interactive run — what is best-effort is only the *outcome*, not the attempt. So it is **non-fatal**: the dashboard only observes, so if Python is missing or the launch fails, say so in one line and carry on — its absence must never block the issue-to-PR pipeline; but silently not attempting the launch is a different failure and is not allowed. It is **idempotent across resumes**: the dashboard's own singleton reuses an already-running current-version server and does not pop a second browser tab, so firing this on every resume is quiet by design. **Skip it in a non-interactive run** (the Degradation case) — no one is watching a headless server, and the human can open it themselves when they resume interactively. The dashboard is a sibling skill in this same `issue-to-pr-pipeline` plugin, so it is always present alongside `resolve-issue`, but it is observational and sits outside the pipeline order — which is why it lives in the preamble, not as a numbered pipeline step.
